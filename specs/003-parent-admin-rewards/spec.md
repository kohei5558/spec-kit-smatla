# Feature Specification: 保護者管理画面と実物景品交換システム

**Feature Branch**: `003-parent-admin-rewards`  
**Created**: 2026 年 1 月 25 日  
**Status**: Draft  
**Input**: User description: "保護者が報酬（実物景品）を管理できる管理画面を実装します。子供が欲しい実物（駄菓子、ポケカ等）をポイント交換できるよう、申請・承認フローを追加します。認証システムも実装し、保護者と子供のアカウントを分離します。"

## Clarifications

### Session 2026-01-25

**Q: 報酬の種類は？**  
A: 実物景品（駄菓子、ポケカ、おもちゃ、文房具など）。既存の仮想アイテム（バッジ、アバター）は削除する。

**Q: 交換フローは？**  
A: 子供が申請 → 保護者が承認 → 実物を渡す。即座交換から申請・承認フローに変更。

**Q: 認証は必要？**  
A: はい。保護者はパスワード認証、子供は保護者が作成した簡易アカウント。

**Q: 複数の子供は？**  
A: 1家庭に複数の子供アカウントを作成可能。

**Q: 通知方法は？**  
A: アプリ内通知。保護者ダッシュボードに未承認申請のバッジ表示。

**Q: 既存データは？**  
A: バッジ・アバター・キャラクターは削除し、実物景品のサンプルマスタデータ（駄菓子、ポケカなど）を初期値として登録。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 保護者が実物景品を登録・管理する (Priority: P1) 🎯 MVP

保護者が管理画面から、子供が交換できる実物景品（駄菓子、ポケカなど）を登録・編集・削除できる。景品ごとに必要ポイント、在庫数、画像を設定できる。

**Why this priority**: 実物景品交換システムの根幹。これがなければ保護者が景品を管理できない。

**Independent Test**: 保護者アカウントでログインし、報酬マスタ管理画面で景品を追加・編集・削除し、データベースに反映されることを確認。

**Acceptance Scenarios**:

1. **Given** 保護者が管理画面の報酬マスタ管理にアクセスした状態で、**When** 「新規景品追加」をクリックする、**Then** 景品名、説明、必要ポイント、在庫数、カテゴリ、画像を入力するフォームが表示される
2. **Given** 景品追加フォームが表示されている状態で、**When** 「うまい棒 コンポタ味」、必要ポイント10、在庫20個、カテゴリ「駄菓子」、画像をアップロードして登録する、**Then** 景品一覧に追加され、子供画面で表示される
3. **Given** 景品一覧が表示されている状態で、**When** 既存景品の編集ボタンをクリックし、必要ポイントを変更して保存する、**Then** 変更が反映される
4. **Given** 景品一覧が表示されている状態で、**When** 在庫が0の景品を削除する、**Then** 削除され、子供画面で非表示になる
5. **Given** 景品追加フォームで、**When** 画像ファイルをアップロードする、**Then** 画像が保存され、景品カードに表示される

---

### User Story 2 - 子供が実物景品の交換を申請する (Priority: P1) 🎯 MVP

子供が獲得したポイントを使って、保護者が登録した実物景品の交換を申請できる。申請時に在庫とポイントをチェックし、条件を満たせば申請状態になる。

**Why this priority**: 子供側の交換フローの核心。申請機能がなければ交換できない。

**Independent Test**: 子供アカウントでログインし、ポイント十分な状態で景品を選択し、交換申請が完了することを確認。

**Acceptance Scenarios**:

1. **Given** 子供が100ポイント保有している状態で、**When** 景品一覧（報酬交換画面）を開く、**Then** 交換可能な景品（100ポイント以下）と交換不可の景品が表示される
2. **Given** 景品一覧が表示されている状態で、**When** 「ポケカ1パック（必要200ポイント）」を選択する、**Then** 「ポイントが不足しています」というメッセージが表示される
3. **Given** 景品一覧が表示されている状態で、**When** 「うまい棒（必要10ポイント）」を選択して交換申請する、**Then** 確認ダイアログが表示され、「申請する」をクリックすると申請が完了する
4. **Given** 交換申請が完了した状態で、**When** 申請一覧画面を開く、**Then** 申請した景品が「申請中」ステータスで表示される
5. **Given** 景品が在庫切れ（0個）の状態で、**When** その景品を選択しようとする、**Then** 「在庫切れ」と表示され、交換申請できない

---

### User Story 3 - 保護者が交換申請を承認・却下する (Priority: P1) 🎯 MVP

保護者がダッシュボードで子供の交換申請を確認し、実物を渡したら「承認」、渡せない場合は「却下」できる。承認するとポイントが消費され、在庫が減少する。

**Why this priority**: 申請・承認フローの後半部分。保護者が承認しなければ交換が完了しない。

**Independent Test**: 子供が申請した後、保護者アカウントで承認し、ポイント消費と在庫減少が反映されることを確認。

**Acceptance Scenarios**:

1. **Given** 子供が交換申請した状態で、**When** 保護者がダッシュボードにアクセスする、**Then** 未承認申請件数がバッジで表示される
2. **Given** ダッシュボードに未承認申請が表示されている状態で、**When** 「交換申請一覧」をクリックする、**Then** 申請中の景品、子供の名前、必要ポイント、申請日時が一覧表示される
3. **Given** 交換申請一覧が表示されている状態で、**When** 申請を選択して詳細を確認し、実物を渡した後「承認」ボタンをクリックする、**Then** 子供のポイントが消費され、在庫が1減り、ステータスが「承認済み」になる
4. **Given** 交換申請詳細が表示されている状態で、**When** 却下理由を入力して「却下」ボタンをクリックする、**Then** ステータスが「却下」になり、子供にポイントが返却される
5. **Given** 承認済みの申請が表示されている状態で、**When** 承認履歴を確認する、**Then** 承認日時、渡した景品が記録されている

---

### User Story 4 - 保護者と子供のアカウントでログインする (Priority: P1) 🎯 MVP

保護者はパスワードでログインし、管理画面にアクセスできる。子供は保護者が作成した簡易アカウントでログインし、問題解答と交換申請のみできる。

**Why this priority**: 認証なしでは保護者・子供の区別ができず、セキュリティリスクが発生する。

**Independent Test**: 保護者アカウントでログインして管理画面にアクセスでき、子供アカウントでは管理画面にアクセスできないことを確認。

**Acceptance Scenarios**:

1. **Given** アプリを起動した状態で、**When** ログイン画面が表示される、**Then** 「保護者ログイン」と「子供ログイン」の選択肢が表示される
2. **Given** 「保護者ログイン」を選択した状態で、**When** メールアドレスとパスワードを入力してログインする、**Then** 保護者用ダッシュボードが表示される
3. **Given** 「子供ログイン」を選択した状態で、**When** 子供の名前を選択（またはPIN入力）する、**Then** 子供用のホーム画面が表示される
4. **Given** 保護者がログインしている状態で、**When** 「子供アカウント管理」にアクセスし、新しい子供アカウントを追加する、**Then** 子供の名前、アバター、PINを設定できる
5. **Given** 子供がログインしている状態で、**When** 管理画面のURLに直接アクセスしようとする、**Then** アクセスが拒否され、「権限がありません」というメッセージが表示される

---

### User Story 5 - 保護者がダッシュボードで子供の学習状況を確認する (Priority: P2)

保護者がダッシュボードで、子供ごとの学習進捗（解いた問題数、正答率、獲得ポイント）、未承認の交換申請件数を一目で確認できる。

**Why this priority**: 保護者の利便性を高める機能だが、MVP には必須ではない。

**Independent Test**: 複数の子供が問題を解き、ポイントを獲得し、交換申請した状態で、保護者ダッシュボードに統計が表示されることを確認。

**Acceptance Scenarios**:

1. **Given** 保護者が複数の子供アカウントを管理している状態で、**When** ダッシュボードを開く、**Then** 各子供の名前、今週解いた問題数、正答率、保有ポイントが表示される
2. **Given** ダッシュボードが表示されている状態で、**When** 未承認の交換申請がある、**Then** 赤色のバッジで件数が表示される
3. **Given** ダッシュボードが表示されている状態で、**When** 子供の名前をクリックする、**Then** 詳細な学習履歴（日別グラフ、カテゴリ別正答率など）が表示される

---

### Edge Cases

- **在庫管理**: 交換申請中に別の子供が同じ景品を申請し、在庫が不足した場合の処理は？ → 申請時点で在庫を仮押さえ（ロック）し、却下時に戻す
- **ポイント不足**: 申請後、保護者が承認する前に別の交換でポイントを使い切った場合は？ → 承認時に再チェックし、不足していればエラー表示
- **画像アップロード**: 大きすぎる画像ファイルをアップロードした場合は？ → サイズ制限（5MB）を設け、超過時はエラー表示
- **複数デバイス**: 保護者がスマホとタブレットで同時にログインした場合は？ → セッション管理を実装し、最新ログインを優先
- **子供の削除**: 子供アカウントを削除した場合、その子供の学習履歴は？ → 論理削除（非表示）とし、データは保持
- **申請のキャンセル**: 子供が申請をキャンセルできるか？ → 申請中ステータスのみキャンセル可能、承認済みはキャンセル不可

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: システムは保護者アカウント（メールアドレス、パスワード）と子供アカウント（名前、PIN）を作成・管理できなければならない
- **FR-002**: システムは保護者と子供のロールを区別し、アクセス権限を制御できなければならない（保護者=管理者、子供=利用者）
- **FR-003**: システムは保護者が実物景品（名前、説明、必要ポイント、在庫数、カテゴリ、画像）を登録・編集・削除できなければならない
- **FR-004**: システムは景品の在庫を管理し、在庫切れの景品を子供画面で非表示にできなければならない
- **FR-005**: システムは子供が保有ポイント以下の景品のみ交換申請できるよう制御しなければならない
- **FR-006**: システムは子供の交換申請を記録し、ステータス（申請中、承認済み、却下）を管理できなければならない
- **FR-007**: システムは保護者が交換申請を承認・却下できなければならない
- **FR-008**: システムは承認時に子供のポイントを消費し、景品の在庫を減らさなければならない
- **FR-009**: システムは却下時に子供にポイントを返却しなければならない
- **FR-010**: システムは保護者ダッシュボードに未承認申請件数をバッジ表示できなければならない
- **FR-011**: システムは保護者が景品画像をアップロードできなければならない（最大5MB、JPEG/PNG形式）
- **FR-012**: システムは保護者が複数の子供アカウントを作成・管理できなければならない
- **FR-013**: システムは保護者が子供の学習状況（問題数、正答率、ポイント）をダッシュボードで確認できなければならない

### Non-Functional Requirements

- **NFR-001**: 画像アップロードは5MB以下に制限され、超過時はわかりやすいエラーメッセージを表示する
- **NFR-002**: 保護者のパスワードは8文字以上、英数字混在を要求し、bcrypt等でハッシュ化して保存する
- **NFR-003**: 申請・承認フローの状態遷移はトランザクション処理で一貫性を保証する
- **NFR-004**: 在庫のロック機構により、同時交換申請時の在庫マイナスを防ぐ
- **NFR-005**: 子供用UIは小学3年生でも操作しやすいよう、大きなボタンと平易な言葉を使用する
- **NFR-006**: 保護者用UIはダッシュボード形式で、一目で状況を把握できるデザインとする

### Data Requirements

- **DR-001**: Userテーブルに保護者と子供を格納し、UserRoleで区別する（Parent, Child）
- **DR-002**: Rewardテーブルに在庫数（Stock）、画像パス（ImagePath）、カテゴリ（RewardCategory）を追加する
- **DR-003**: AcquiredRewardテーブルにステータス（ExchangeStatus: Pending, Approved, Rejected）、承認日時、却下理由を追加する
- **DR-004**: 既存の仮想アイテム（バッジ、アバター、キャラクター）は削除し、実物景品のサンプルデータ（駄菓子、ポケカなど10〜20個）をシードする

### Success Criteria

- **SC-001**: 保護者が5分以内に新しい景品を登録できる
- **SC-002**: 子供が交換申請から承認までのステータスをリアルタイムで確認できる
- **SC-003**: 保護者ダッシュボードに未承認申請がある場合、3秒以内にバッジが表示される
- **SC-004**: 在庫切れの景品は子供画面で即座に非表示になる
- **SC-005**: 承認・却下処理は2秒以内に完了し、ポイントと在庫が正しく反映される
- **SC-006**: 画像アップロードは3秒以内に完了し、プレビューが表示される

## Out of Scope

- メール通知機能（プッシュ通知、メール通知は今回は実装しない）
- 外部決済システム連携（実物景品の購入は保護者が別途行う）
- 複数保護者アカウント（1家庭1保護者アカウントのみ）
- 子供同士のポイント譲渡・競争機能
- リアルタイム通知（WebSocketやPush通知は不要、ポーリングまたは画面更新）

## Technical Notes

### 認証方式

- 保護者：JWT トークン認証（メールアドレス + パスワード）
- 子供：簡易認証（名前選択 + 4桁PIN、またはトークンレス）

### 画像ストレージ

- ローカルファイルシステム（`wwwroot/uploads/rewards/`）または Azure Blob Storage
- ファイル名はGUID + 拡張子

### 在庫ロック

- 楽観的ロック（RowVersion）または悲観的ロック（トランザクション）
- 申請時に在庫をデクリメント、却下時にインクリメント

### データ移行

- 既存 Reward テーブルの全レコードを削除
- 新しいスキーマ（Stock, ImagePath, IsPhysical）でマイグレーション実行
- 実物景品サンプルデータをシード（うまい棒10pt、ポケカ1パック200ptなど）
